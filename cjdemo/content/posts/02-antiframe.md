## 제품 한 줄 정의

Antiframe은 **대본을 넣으면 영상 초안을 만들고, 필요한 부분만 말로 고쳐 최종 영상까지 완성하는 웹 기반 영상 제작 도구**입니다.

숏애니 제작에서 여러 생성 도구를 오가며 같은 정보를 반복 입력하고, 한 장면의 오류 때문에 전체 공정을 다시 실행하는 문제를 경험했습니다. 이 개인 프로젝트에서는 그 제작 경험을 하나의 제품 흐름으로 바꿨습니다.

![Antiframe 랜딩 화면](assets/projects/antiframe/landing.png)

## 1. 해결하려 한 제작 문제

기존 AI 영상 제작에서는 대본, 음성, 이미지, 영상과 편집 도구가 분리되어 있었습니다. 사용자는 각 도구의 용어와 입력 형식을 익히고, 앞 단계의 결과를 다음 단계에 다시 입력해야 했습니다.

실제 제작에서 더 큰 문제는 생성 자체보다 다음 세 가지였습니다.

- 작업이 어디까지 진행됐는지 추적하기 어렵습니다.
- 한 장면이 잘못되면 무엇을 다시 만들어야 하는지 알기 어렵습니다.
- 자동 생성과 제작자의 판단이 필요한 지점이 구분되지 않습니다.

Antiframe은 이 문제를 `대본 → 영상 초안 → 장면 검토 → 필요한 장면 수정 → 최종 영상`이라는 작업 흐름으로 재구성했습니다.

> 제품의 중심을 생성 기능의 수가 아니라, 제작자가 결과를 확인하고 다음 판단을 내리는 순서에 두었습니다.

## 2. 기능보다 먼저 제품 언어를 정했습니다

사용자에게 `storyboard`, `asset`, `TTS`, `render` 같은 내부 용어를 그대로 보여주지 않았습니다. 제작 프로그램에 익숙하지 않은 사용자도 다음 행동을 이해하도록 문구를 바꿨습니다.

- storyboard → **영상 초안**
- cut → **장면**
- asset → **화면 또는 영상 자료**
- TTS → **내레이션 또는 목소리**
- render → **최종 영상 만들기**
- failed → **오류 상태와 다음 행동**

이 기준은 화면 카피에만 적용되지 않습니다. 내부 상태가 복잡해져도 사용자는 현재 해야 할 일 하나를 이해할 수 있어야 한다는 제품 원칙입니다.

## 3. 전공정: 제작 조건을 한 번만 입력합니다

처음부터 모든 설정을 한 화면에 펼치지 않았습니다. 사용자는 다음 순서로 영상의 조건을 정합니다.

1. 세로형 숏폼 또는 가로형 롱폼 선택
2. 영상의 주제와 카테고리 입력
3. 설명에 필요한 키워드 정리
4. 직접 작성하거나 보조받은 대본 확인
5. 내레이션 목소리 선택

![한 화면에서 하나의 판단만 하도록 구성한 영상 형식 선택 화면](assets/projects/antiframe/format-select.png)

![대본의 성격에 맞는 내레이션을 고르는 화면](assets/projects/antiframe/voice-select.png)

형식과 음성처럼 결과 전체에 영향을 주는 결정은 사용자에게 남기고, 대본을 장면으로 나누거나 반복 입력을 변환하는 작업은 시스템이 이어서 수행하도록 설계했습니다.

## 4. 후공정: 대본을 검수 가능한 장면으로 바꿉니다

대본 입력이 끝나면 별도의 `생성 시작` 버튼을 반복해서 누르게 하지 않습니다. 시스템은 대본을 장면 단위로 나누고, 각 장면에 필요한 정보를 묶습니다.

- 장면이 영상에서 담당하는 역할
- 화면에 전달해야 할 핵심 정보
- 내레이션 원문과 실제 발음용 문장
- 이미지·영상 자료를 찾거나 생성하기 위한 시각 정보
- 장면의 길이와 전환 방식
- 현재 생성 상태와 다시 실행할 수 있는 범위

사용자는 완성된 초안을 기준으로 장면을 검토합니다. 제작 파이프라인의 내부 단계가 아니라, **어느 장면이 의도와 다른지**를 보게 하는 것이 목적입니다.

## 5. 자연어 수정은 장면 선택부터 시작합니다

영상 전체를 채팅으로 다시 만드는 방식은 통제 범위가 불명확합니다. Antiframe의 수정 흐름은 먼저 장면을 고르고, 그 장면 안에서 바꿀 요소를 해석합니다.

예를 들어 사용자가 `두 번째 장면의 설명을 더 쉽게 하고, 화면은 수치가 보이는 자료로 바꿔줘`라고 입력하면 다음처럼 분리합니다.

1. 대상은 두 번째 장면으로 고정합니다.
2. 내레이션 문장과 화면 자료가 변경 대상입니다.
3. 다른 장면, 선택한 목소리와 전체 영상 형식은 유지합니다.
4. 변경된 요소만 다시 만들고 결과를 비교합니다.

요청이 `더 좋게 바꿔줘`처럼 넓으면 즉시 전체를 수정하지 않습니다. 더 쉽게, 더 역동적으로, 더 차분하게, 화면 위주로 같은 선택지를 제시하거나 추가 질문으로 범위를 좁힙니다.

## 6. Human Checkpoint를 남긴 기준

자동화는 버튼을 없애는 것이 아니라, 불필요한 판단을 없애는 일로 정의했습니다.

### 시스템이 자동으로 이어가는 단계

- 대본을 장면 단위로 구조화
- 앞 단계의 입력값을 다음 단계 형식으로 변환
- 장면별 생성 상태와 결과 저장
- 완료된 단계는 유지하고 필요한 단계만 재실행
- 최종 영상 제작에 필요한 파일과 정보를 조립

### 사용자가 확인하는 단계

- 영상 형식과 전달 목적
- 대본의 내용과 목소리
- 장면 구성이 의도와 맞는지
- 자연어 수정 요청의 대상과 범위
- 배경음악·자막과 최종 제작 실행

이 구분은 비용과 품질을 동시에 다룹니다. 생성 비용이 드는 변경은 사용자의 의도를 확인한 뒤 실행하고, 단순한 데이터 변환과 상태 연결은 자동화합니다.

## 7. 실패를 막다른 화면으로 만들지 않았습니다

생성 파이프라인에서는 외부 API, 파일 저장과 렌더 작업이 각각 다른 이유로 멈출 수 있습니다. 처음부터 모든 오류를 `다시 만들기` 하나로 처리하면 이미 완료된 결과까지 잃고 비용을 반복하게 됩니다.

그래서 실패 상태를 공정과 장면 단위로 기록하고, 돌아갈 수 있는 위치를 분리했습니다.

- 초안 구조 오류 → 대본 분석 단계만 재시도
- 특정 장면 자료 오류 → 해당 장면의 자료만 다시 생성
- 내레이션 발음 오류 → 발음용 문장과 음성만 수정
- 최종 영상 오류 → 장면 결과는 유지하고 최종 제작만 재시도
- 수정 후 최종 영상이 오래된 상태 → 기존 결과를 폐기하지 않고 재제작 필요 상태 표시

오류 메시지에는 내부 시스템명보다 사용자가 다음에 할 수 있는 행동을 표시했습니다. 운영 기록에는 실패 원인을 남기되, 사용자 화면에서는 `어떤 장면을 다시 만들면 되는지`가 먼저 보이도록 했습니다.

## 8. 문서가 코드보다 먼저 바뀌는 운영 방식

Antiframe은 기능을 추가할 때 바로 화면부터 수정하지 않았습니다.

1. 제품 기준 문서에서 사용자 흐름과 문구를 먼저 변경합니다.
2. 바뀐 기준에 따라 화면과 파이프라인을 구현합니다.
3. 구현 후 실제 화면이 기준 문서와 같은지 QA합니다.
4. 스펙이 잘못됐다면 코드에 예외를 더하기 전에 문서를 수정합니다.

이 방식으로 제품 정의, 용어 사전, 페이지 목적, 상태 문구, 오류 처리와 QA 기준을 한 문서에서 관리했습니다. 변경 이력에는 무엇을 고쳤는지만이 아니라 문제가 발생한 조건과 검증 결과를 함께 남겼습니다.

## 9. 구현 구조

제품은 Next.js와 TypeScript 기반의 웹 애플리케이션으로 구현했습니다. 제작 흐름을 화면 단위가 아니라 프로젝트 상태로 이어지게 설계하고, 다음 영역을 분리했습니다.

- **전공정 화면:** 형식, 주제, 키워드, 대본과 목소리 입력
- **프로젝트 작업실:** 장면별 초안, 생성 상태와 수정 이력
- **자연어 수정:** 대상 장면과 변경 필드를 구조화
- **생성 API:** 대본 분석, 음성, 화면 자료와 장면 처리
- **최종 제작:** 완료된 장면을 묶어 영상 파일 생성
- **운영·QA:** 중단된 작업, 외부 API 오류와 재시도 기록

외부 서비스를 하나로 고정하지 않고 공정별 역할로 분리했습니다. 텍스트 구조화, 내레이션, 자료 검색·생성, 영상 조립은 각자의 입출력과 실패 상태를 갖습니다. 따라서 한 서비스의 오류가 전체 프로젝트를 처음으로 되돌리지 않도록 했습니다.

## 10. 초기 사용자 검증

초기 사용자 42명이 제품을 사용했고, 설문 응답자 39명 가운데 37명이 지속 사용 의향을 보였습니다.

이 수치는 완성된 시장 검증으로 과장하지 않습니다. 초기 단계에서 확인한 것은 다음 두 가지입니다.

1. 편집 타임라인보다 대본과 장면 중심의 흐름을 이해할 수 있는가
2. 전체 재생성보다 필요한 장면만 자연어로 수정하는 방식에 사용 의향이 있는가

사용 과정에서 발견된 혼란은 제품 기준 문서와 화면 문구에 반영했습니다. 특히 사용자가 내부 공정명을 추적해야 했던 화면을 작업 행동 중심으로 바꾸고, 생성 후 다음 버튼을 찾는 단계를 줄였습니다.

## 11. 숏애니 경험이 제품으로 확장된 지점

숏애니에서는 얼굴·그림체·배경을 레이어로 분리해 움직일 대상만 바꿨습니다. Antiframe에서는 같은 원리를 제작 공정 전체에 적용했습니다.

- 한 화면의 레이어 → 한 프로젝트의 제작 단계
- 움직일 요소 → 사용자가 수정 요청한 장면과 필드
- 보존 요소 → 이미 승인된 다른 장면과 설정
- 실패 원인 진단 → 특정 단계만 재실행하는 상태 구조

Layer-in-Layer가 생성 프롬프트를 통제하는 방식이었다면, Antiframe은 **제작 시스템에서 유지할 것과 다시 만들 것을 분리하는 방식**입니다.

## 기여 범위와 사용 기술

- **기여도 100%:** 제품 기획, UX 문구, 정보 구조, 프론트엔드·API 구현, 생성 파이프라인 연결, 운영 문서와 QA
- **Web:** Next.js 14, React, TypeScript
- **Media:** FFmpeg 기반 최종 영상 처리
- **구조:** 프로젝트 상태 저장, 장면 단위 생성·수정, 단계별 재시도
- **운영:** 제품 스펙, 패치 노트, 인수 문서와 반복 QA

포트폴리오의 인터랙티브 데모는 채용 검토 환경에서 안전하게 확인할 수 있도록 API, 계정, 데이터 저장과 외부 생성 비용을 연결하지 않았습니다.
